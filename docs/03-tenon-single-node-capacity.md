# 03 单机容量：tenon 完整链路在 2 核 2G 上能承载多少

## 环境

- 阿里云经济型实例，2 vCPU（x86_64）、2GB 内存（可用约 1.7GiB）、ESSD 云盘，新加坡地域，Ubuntu 26.04。
- PostgreSQL 18（`wal_level=logical`，`shared_buffers=256MB`）、NATS 2.15（JetStream）、应用全部在这一台机器上，模拟“单机部署”。
- 应用是 `tools/tenonload`：多个 goroutine 按指定速率开事务，插入一行业务数据并 `Topic.Publish` 一个任务；同一个进程中运行 tenon 的 worker（框架的 `start` 命令也是这样把 HTTP 和 worker 放在一起）。任务经过 WAL → 逻辑复制槽 → relay → JetStream → worker，统计从提交到开始处理的端到端延迟。
- 框架默认值：连接池 8 个连接（4 × 核数），每个 topic 并发 10。

脚本：`scripts/ecs/capacity.sh`；原始结果：`results/ecs/01`–`04`。

## 结论

| 场景 | 稳定承载 | 上限 | 瓶颈 |
|---|---|---|---|
| 处理函数为空 | 1500–2000/s | 约 1800/s（relay 修复后） | 整机 CPU，PostgreSQL 占得最多 |
| 处理函数更新一行数据 | **约 1000/s** | 1500/s 时处理速度掉到约 700/s，积压持续增长 | 共用的连接池（8 个）和 PostgreSQL 的 CPU |

约 1000 任务/秒相当于每天 8600 万个任务。满载时 CPU（100% = 1 核）：应用约 68%、PostgreSQL 约 84%、NATS 只有 15–30%；内存：应用约 23MB、PostgreSQL 进程约 20MB（另有共享缓冲区）、NATS 13–100MB。**NATS 不是瓶颈。**

要承载更多：把 worker 拆到另一个进程或机器、调大连接池、PostgreSQL 单独部署。

## 发现一：不要用 Docker 端口映射连 PostgreSQL

第一轮用 `-p 127.0.0.1:5432:5432` 映射端口，上限只有约 1300/s。满载时 `top`：

```
docker-proxy（PostgreSQL 的端口转发）  37.5%
docker-proxy（NATS 的端口转发）         4.4%
软中断                                 约 10%
```

改成 host 网络、只监听 127.0.0.1 后，上限到约 2350/s。生产环境要么直接在宿主机上装 PostgreSQL，要么容器用 host 网络。

## 发现二：relay 攒批的延迟问题（已修复，tenon PR #105）

host 网络下，处理函数为空时：

| 速率 | 事务 p99 | 端到端 p50 | 端到端 p99 |
|---|---|---|---|
| 500/s | 5ms | 9ms | 36ms |
| 1000/s | 8ms | **91ms** | **481ms** |
| 2000/s | 44ms | 86ms | 252ms |

速率翻倍，延迟反而升了一个数量级。原因：relay 的注释写“攒批最多等 2ms”，实现却是每收到一个任务就把截止时间推后 2ms。任务间隔小于 2ms 时计时器一直不触发，要攒满 500 条才发出。

修复为“从一批中的第一个任务到达起最多等 2ms”：

| 速率 | 修复前 p50 / p99 | 修复后 p50 / p99 |
|---|---|---|
| 1000/s | 91 / 481ms | 5 / 15ms |
| 1500/s | 102 / 336ms | 6 / 22ms |
| 1000/s，处理函数更新一行 | 130 / 510ms | 13 / 213ms |

代价：批次变小、往返变多，不限速时的上限从约 2350/s 降到约 1800/s，NATS 的 CPU 从约 16% 升到约 30%。试过把向 PostgreSQL 报告确认位置的频率降到每 3 秒一次，吞吐没有变化，没有采用。实际部署不会长期跑在上限附近，正常负载下的延迟更重要。

## 发现三：定时消息的内存

tenon 把 `max_defer`（默认 1 小时）以内的延迟任务和重试交给 JetStream 的定时消息，每条定时消息独占一个 subject。实测（`results/ecs/04-schedule-memory.txt`）：重启后加载 24 万条定时消息，NATS 占 198MB，**约 0.75KB/条**，100 万条约 750MB。

比如下游宕机 15 分钟、期间每秒 1000 个任务全部失败，按退避时间（1 秒、16 秒、81 秒、约 4 分钟、约 10 分钟……）都会进入定时消息，就接近这个量。小机器上：

- 把 `max_defer` 调小（例如 10 分钟），更晚的延迟和重试存入 PostgreSQL 的 `queue_scheduled`；
- 下游故障时在 tenon 的队列面板上先暂停对应的 topic。

## 发现四：磁盘同步策略

见 [04 单机部署](04-deploy-single-node.md#磁盘同步)：`sync_interval: always` 在这块云盘上只有约 450 条/秒，`1s` 只慢 5–10%。
